# AI Agent 开发学习教科书

这套资料面向已经具备后端工程经验、能够调用大模型 API，但希望系统理解 Agent 工程原理的开发者。

## 学习目标

完成这套教材之后，你应该能够回答下面这些问题：

1. 一个普通 LLM 调用和一个 Agent 到底差在哪里？
2. Tool Calling、Agent Loop、ReAct、Workflow、Planning 分别解决什么问题？
3. 多轮对话为什么“看起来像有记忆”，它和真正的 Memory 有什么区别？
4. State、Memory、RAG、Context 分别应该保存什么？
5. Context 为什么会越来越大？什么时候应该做选择、摘要、压缩和外部化？
6. Agent Harness 到底是什么？为什么复杂 Agent 最终都需要 Harness？
7. 如何让 Agent 能够中断恢复、长时间运行、自我检查？
8. Multi-Agent 什么时候值得使用，什么时候反而会把系统做复杂？
9. Tool、Skill、MCP 的边界是什么？
10. Guardrail、Human-in-the-loop、Sandbox、Tracing、Evaluation 应该放在哪一层？
11. 当你以后接触 Spring AI、LangChain4j、LangGraph、Claude Code、Codex 或其它框架时，能够看出它们分别替你封装了哪些基础机制。

## 技术基线

所有 Demo 默认采用：

- JDK 21
- Maven
- 本地 SQLite
- Java 标准 `HttpClient` 优先
- JSON：Jackson
- SQLite 驱动：`org.xerial:sqlite-jdbc`
- 测试：JUnit 5
- 日志：优先 `java.util.logging` 或简单控制台输出，必要时才引入 SLF4J
- Stage Web：JDK `HttpServer` + HTML/CSS/原生 JavaScript

除非章节明确要求，否则：

- 不使用 Spring Boot
- 不使用 ORM
- 不使用 LangChain4j / Spring AI / LangGraph 等 Agent 框架
- 不使用消息队列、Redis、Docker、Kubernetes
- 不使用 Vue / React / Node/npm 等前端工程化工具链
- 不为了“工程化”增加与当前教学目标无关的模块

这么做不是因为这些技术不好，而是为了让 Agent 的核心机制直接暴露出来。

## 统一业务世界：AI 任务助手

所有实验尽量围绕同一个业务世界展开：

> 用户通过自然语言给 AI 一个任务。AI 可以查询任务、创建任务、读取资料、执行简单计算、保存偏好、制定计划、恢复历史任务，最终逐渐演变成一个具有状态、记忆、规划和工具调用能力的 Agent。

但每个 Lab **代码上尽量独立**。

这样可以同时获得两个好处：

- 业务语义连续，不需要每章重新理解一个新业务；
- 代码不会无限继承历史包袱，每章可以清楚观察一个机制。

## 推荐使用方式

每一章按下面顺序进行：

1. 阅读章节概念。
2. 不写代码，先尝试回答“本章自测”。
3. 阅读章节里的实现思路。
4. 把对应 `docs/prompts/` 文件交给你当前使用的 AI 编程工具。
5. 运行 Demo。
6. 主动修改几个参数或故意制造错误。
7. 回到教材回答“观察题”。
8. 对照答案。
9. 每 3~4 个章节做一次 `docs/stages/` 中定义的阶段综合项目。

**不要追求第一次就写出漂亮架构。**

这套教材最重要的教学方法是：

> 先遇到问题，再引入概念解决问题。

例如：
- 先让对话历史无限增长，再学习 Context Compression；
- 先让任务崩溃后全部重来，再学习 Checkpoint；
- 先让模型自己判断 JSON 合不合法，再用代码做 Deterministic Validation。

只有真正见过“没有这个机制时会发生什么”，概念才会变得牢固。

## 学习顺序

建议严格按以下顺序：

1. LLM 与 Agent 的边界
2. Structured Output 与 Tool Calling
3. Agent Loop 与 ReAct
4. Workflow Patterns
5. Planning / Plan-and-Replan
6. Multi-turn Conversation 与 State
7. Memory
8. RAG / Memory / Context
9. Context Engineering / Compression
10. Harness / Checkpoint / Long-running Agent
11. Reflection / Evaluator / Deterministic Validation
12. Multi-Agent
13. Skill / MCP
14. Guardrail / HITL / Sandbox
15. Observability / Evaluation
16. 最后再映射到 Agent Framework

## 关于模型 API

教材不绑定某一家模型供应商。

建议在代码中抽象：

```java
public interface LlmClient {
    LlmResponse chat(List<Message> messages, List<ToolDefinition> tools);
}
```

具体实现可以读取：

```text
LLM_BASE_URL
LLM_API_KEY
LLM_MODEL
```

只要供应商提供 OpenAI-compatible Chat API，就可以写一个兼容实现。

学习阶段的重点不是 SDK，而是你自己代码里的：

```text
Context -> LLM -> Action -> Tool -> Observation -> State
```

这个循环。


## AI 编程工具兼容原则

教材和 `docs/prompts/` 中的实现 Prompt 不依赖某一个具体 AI 编程产品。

只要工具能够：

- 读取仓库文件；
- 修改 Java / Maven 文件；
- 执行 `mvn`、`java` 或测试命令；
- 查看命令输出；

就可以使用这套教材。

无论使用哪一种 AI 编程工具，都显式要求它先读取根目录 `AGENTS.md`。本仓库维护 `AGENTS.md` 与 `CLAUDE.md` 双镜像，内容一致，修改须同步。

## V3：为什么综合 Stage 增加 Web UI

单一 Lab 用 CLI 更容易看清概念；综合 Stage 的内部状态越来越多，只看最终回答已经不够。

因此交互方式逐步升级：

```text
Stage 1 → CLI
Stage 2 → Chat + State / Memory / Plan
Stage 3 → Long-running Debugger
Stage 4 → Agent Harness Console
```

详细规范见 `docs/04_Web可视化调试台规范.md`。
